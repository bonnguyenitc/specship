### Blockers (first pass)
- [x] [self][blocker] **The review loop-back never closes — no task can reach `done` after a single `changes-requested` review.** Once `review: changes-requested` is set, `computeNextPhase` short-circuits and only ever accepts `coding` or `debug`; there is no reachable path back to `review`, and therefore none to `review: approved` → `done`. Reproduced: `coding: done` + `review: changes-requested` + `next_phase: review` → `next_phase: null`, `valid: false`, `check --phase review` exit 1. The task is unrunnable — every phase is refused. This directly contradicts the text shipped in the same change: `debug/SKILL.md` instructs *"set `next_phase:` back to that phase [`coding` or `review`]"*, and the `WORKFLOW.md` gate table says *"debug `clear` → back to `resume_phase`"*. Nothing in the contract ever resets `review` out of `changes-requested`. Breaks the consumer requirement this task exists to serve (App Builder `TASK-049` R20/AC16: *"return to the interrupted phase"*). Ref `src/pipeline.js:185-190`.
- [x] [code-review][blocker] **A `#` comment or blank line inside `artifacts:` silently voids the entire map — and the task still reports `valid: true`.** The nested map only opens when the *next* line matches an indented `key:`; once `nest` is null, indented lines fall through. `parseFrontmatter`'s own docblock advertises `# comments` support. Reproduced on a `stage: done` task with a `# current states` comment: all five artifacts read `missing`, `next_phase: "spec"`, `valid: true`, `issues: []`, and `check --phase spec` exits **0** — the orchestrator re-runs `spec` over finished work. Fails **open**, which is what R3's fail-closed rule forbids. Same class: a typo'd key inside the block is dropped silently; a duplicate key last-wins. Ref `src/pipeline.js:47-57`.
- [x] [code-review][blocker] **`check --phase` without a task id ignores the gate and exits 0.** `cmdCheck` only routes to `cmdCheckPhase` when a positional is present, so `--phase`/`--actor`/`--expect-revision`/`--json` are all silently discarded and the repo-wide check runs instead. Reproduced in a clean project: `check --phase review --actor codex --expect-revision 99 --json` → human text on stdout, **exit 0** — the documented "gate is valid, run the phase" signal, with revision 99 never compared. An orchestrator that loses the id gets a green light for an arbitrary phase. Should be exit 2. This also makes `WORKFLOW.md`'s *"`specship check --actor <them>` exits 2"* false — reproduced: exit **0**. Ref `src/cli.js:274`.
- [x] [code-review][blocker] **`checkPhase` never enforces the "Flow integrity" preconditions `WORKFLOW.md` promises it enforces.** The contract states: *"confirm … the preconditions in 'Flow integrity' hold … **One command does all of it**"*. `checkPhase`'s issues come only from `loadTask`, which reads the `artifacts:` map and never checks whether `spec.md`/`plan.md` exist or what status they carry — those checks live only in `check()`. Reproduced on one task with `task.md` alone on disk claiming `spec: confirmed / plan: approved / coding: done`: `check TASK-002 --phase review --expect-revision 5` → `ok: true`, exit 0, while global `check` on the *same task* reports 2 violations (`spec.md is missing`, `plan.md is missing`). The two validators disagree, and the one the orchestrator is told to trust is the permissive one. AC1 explicitly requires "missing preconditions" coverage. Ref `src/pipeline.js:285-313`.
- [x] [code-review][blocker] **The gate ignores `stage`/`status`, so a shipped legacy v1 task gates back to `spec` as valid.** `computeNextPhase` reads only `artifacts`; a v1 task with no `artifacts:` map defaults all-`missing`. Reproduced on `stage: done, status: done`: `next_phase: "spec"`, `valid: true`, `issues: []`, `check --phase spec --actor codex` → exit **0** — re-running `spec` on shipped work. R9's "safe defaults for legacy v1 tasks" are not safe if nothing reconciles `stage: done` with `next_phase: spec`. The spec's Edge Cases name this exact case: *"A legacy task lacks `artifacts` … or is already done."* Suggest refusing gates for `schema < 2` (exit 2, consistent with the newer-schema path) or making a `done` stage/status contradict a non-null gate. Ref `src/pipeline.js:255,265`.
- [x] [code-review][blocker] **A corrupt or newer-version `.specship/install.json` silently downgrades an orchestrated install, deletes the evidence, and `doctor` then certifies it healthy.** `readProfile` catches *everything* and returns `interactive`, so it cannot distinguish "absent" (default is right) from "present but unreadable" (must refuse); `install()` feeds that inferred default back to `writeProfile`, which unlinks the manifest whenever the profile is `interactive`. Reproduced end-to-end: orchestrated install (`model: inherit`) → corrupt the manifest → `specship update` → **`model: sonnet` re-pinned, manifest DELETED, no warning**, then `doctor` reports *"[profile: interactive] All installed agents are healthy."* Every subsequent orchestrated Claude phase then runs with a pinned model that overrides the launcher's explicit choice — defeating R10 and the module header's own claim (*"so `update`/`doctor` can't silently fall back to the default"*), and breaking `TASK-049` R18/R22 ("never silently substitutes another model"). The spec's Edge Cases name it: *"An orchestrated Claude install is updated after the user chose an explicit model in App Builder."* Zero test coverage for a corrupt or unknown-profile manifest. Suggest: default only on `ENOENT`; refuse on parse failure, unknown `profile`, or a `version` newer than `VERSION`; never unlink a manifest that failed to parse. Ref `src/install-profile.js:21-43`, `src/cli.js:127,135`.

## Commit / PR Draft
```
feat(orchestration): run one workflow phase at a time from an external tool

Add an opt-in external orchestration mode so a tool that owns its own task
board (App Builder TASK-049) can run a single Specship phase, hand the task to
another agent at the next checkpoint, and decide what runs next by reading the
task artifacts. The interactive flow and `ship` are unchanged.

- task.md schema v2: additive `schema`/`revision`/`next_phase`/`resume_phase`;
  `stage`/`status`/`artifacts` remain the source of truth. Legacy v1 tasks read
  with safe defaults and are never rewritten on read.
- `specship inspect <TASK-ID> --json`: read-only normalized state.
- `specship check <TASK-ID> --phase <p> [--actor] [--expect-revision] --json`:
  one command for the whole envelope - task identity, artifact backing, phase
  gate and revision - with exit 0 (run it) / 1 (state or gate invalid) / 2 (bad
  input, unsupported actor/schema, no such task).
- Persisted `orchestrated` install profile (`.specship/install.json`), certified
  for Codex CLI and Claude Code only. Claude stage skills install with
  `model: inherit` so an explicit launcher model wins; Codex output is
  byte-identical either way, and canonical package skills are never mutated.
- The five stage skills gain an "External phase execution" contract: run one
  phase, hydrate from the named task's artifacts, checkpoint task.md last with
  revision +1, stop. `ship`/`resume-task` are excluded, in code and in text.

Zero runtime dependencies. 69 tests green; v0.1.17 -> v0.2.0.

Note for CI: `specship check <stray-word>` now exits 2 with a JSON body
(previously exit 1 with help text). Only already-invalid invocations change.
```

## Follow-ups
- **Seven open `minor` findings** remain unticked in Findings above and are deliberately deferred, not dropped: optional `--actor` (the certification gate is opt-in when the flag is omitted), `check()` not validating v2 fields, `clean()` stripping from the first ` #` without quote handling, `checkPhase`'s JSON shape varying across exit codes (`next_phase`/`revision` absent on some exit-2 paths; `NaN` revision serializing as `null`), `Number()` accepting `0x10`/`1e3` as a revision, symlinked task dirs visible to `loadTask` but not to `check`/`tasks`, and a manifest whose `version` is newer but whose `profile` is known being accepted. None can produce a wrong gate on a well-formed task; each is a hardening or ergonomics item.
- `check <stray-word>` exits 2 instead of 1 (see the commit note) — a CI job asserting 1 on an already-invalid invocation would need updating.
- **For `TASK-049` (App Builder), independent of the blockers:** `check --phase <p>` returns `ok: true` for a task whose `status` is `blocked` — by design (R5: *"any blocker keeps the current phase as the retry target"*), but the `check` body exposes no `status`/`blocked_reason`. An orchestrator trusting exit 0 alone would relaunch a blocked task forever. App Builder must consult `inspect` (which does expose both), or `check`'s body should carry `status`. Worth deciding deliberately rather than by omission.
- ~~Consider whether `resume_phase` earns its place: the gate never reads it (it must be cleared exactly when debug clears), so today it is documentation, not state.~~ **Wrong — retracted 2026-07-17 11:58 +07.** The gate indeed never reads it, but that was the wrong question: the **`debug` agent** reads it, and in external mode it hydrates from artifacts alone. Two states can be identical in every field the gate reads — `stage: review`, `status: blocked`, `coding: done`, `review: changes-requested`, `debug: open-bugs`, `next_phase: debug` — and still demand opposite hand-backs: debug entered *from review* (a defect the review found) must return to `review`, while debug entered *from coding during a review loop-back* must return to `coding` to finish the findings. Only `resume_phase` distinguishes them. Removing it would reintroduce a variant of B1 in the very loop B1 fixed. Kept, and locked with a regression test asserting the two cases are indistinguishable without it (`test/pipeline.test.js` → "resume_phase carries what artifact state cannot"). Lesson recorded as `L4`.
